Revisa todos los cambios en staging (`git diff --staged`) y genera el mensaje de commit.

Formato obligatorio:

<gitmoji> tipo(scope): título corto

<párrafo 1>

<párrafo 2 opcional>

Reglas:

* El resultado final debe contener exclusivamente el mensaje del commit.
* Cualquier texto fuera del mensaje del commit es inválido.
* No agregues líneas adicionales antes o después del commit.
* El Gitmoji debe corresponder al tipo Conventional Commit.

Correspondencia obligatoria:

* ✨ → feat
* 🐛 → fix
* ♻️ → refactor
* ⚡ → perf
* 📚 → docs
* ✅ → test
* 👷 → ci
* 📦 → build
* 🔧 → chore

Arquitectura por tipo (elige según la naturaleza del cambio, no según los archivos):

* `feat` ✨ — nueva capacidad o comportamiento observable.
* `fix` 🐛 — corrige un comportamiento incorrecto existente.
* `refactor` ♻️ — reestructura sin cambiar comportamiento ni API.
* `perf` ⚡ — mejora rendimiento sin cambiar resultados.
* `docs` 📚 — solo documentación.
* `test` ✅ — solo pruebas, sin tocar código de producción.
* `ci` 👷 — pipelines y automatización.
* `build` 📦 — build, dependencias, empaquetado.
* `chore` 🔧 — mantenimiento; último recurso si no encaja en otro tipo.

Reglas de tipo:

* El staging debe representar **una sola** intención funcional. Si lo que está en staging mezcla tipos (p. ej. `feat` + `fix`), DETENTE: no generes un commit mixto; informa que debe separarse.
* `refactor` no cambia comportamiento; si un test tendría que cambiar, es `feat`/`fix`.
* `docs` es puro: documentación mezclada con lógica no es `docs`.

Scope:

* Módulo o dominio afectado (`auth`, `pagos`, `siigo`), en minúsculas.
* Nunca un nombre de archivo, clase o ruta.
* Inclúyelo siempre que exista un área clara; omítelo solo si el cambio es global.

Cambios que rompen compatibilidad:

* Si rompe API/contrato/formato/configuración, marca el tipo con `!` y agrega el pie `BREAKING CHANGE:` con el impacto y la migración. Ejemplo de encabezado: `✨ feat(auth)!: ...`.

Título:

* Debe ser corto, claro y específico.
* Debe describir el estado final del sistema después del cambio.
* Debe leerse como algo que ya forma parte del proyecto.
* No debe sonar como una tarea pendiente.
* No debe estar escrito en infinitivo.
* Debe poder entenderse sin revisar el código.

Evita títulos como:

* implementar paginación server-side
* migrar JWT a RS256
* agregar catálogo SIIGO
* reorganizar validación de tokens

Prefiere títulos como:

* manejo de paginación en los listados
* validación de tokens mediante firmas asimétricas
* catálogo de códigos configurable por empresa
* validación de tokens desacoplada del firmado

Si el título contiene nombres de clases, variables, tablas, métodos o detalles internos de implementación, probablemente está mal redactado.

Cuerpo:

* Debe explicar el propósito y el impacto funcional del cambio.
* Debe estar redactado como si hubiera sido escrito manualmente por el desarrollador.
* Usa lenguaje natural y profesional.
* Prioriza explicar el "qué" y el "por qué" sobre el "cómo".
* Para cambios pequeños utiliza uno o dos párrafos.
* Para cambios amplios puedes utilizar una lista breve únicamente si mejora la legibilidad.

Las listas están permitidas únicamente para resumir funcionalidades o comportamientos relevantes.

No utilizar listas para:

* Enumerar archivos.
* Enumerar clases.
* Enumerar funciones.
* Enumerar tablas.
* Describir cambios línea por línea.

Prohibido:

* Convertir el commit en un changelog.
* Generar secciones como:
  * CAMBIOS:
  * Beneficios:
  * Resumen:
  * Checklist:
  * Referencias:
  * Archivos modificados:
* Incluir métricas, estadísticas o comparaciones.
* Enumerar archivos modificados.
* Explicar cambios archivo por archivo.
* Mencionar herramientas utilizadas para generar el commit.
* Incluir créditos, firmas o atribuciones.

Las siguientes líneas están estrictamente prohibidas:

* Co-Authored-By:
* Generated by
* Created with
* Claude
* Anthropic
* ChatGPT
* OpenAI
* Gemini
* Copilot

Si cualquiera de los elementos anteriores aparece en la salida, el resultado es inválido y debe regenerarse.

Después de generar el mensaje, ejecuta `git commit` utilizando exactamente ese mensaje y nada más.

Antes de ejecutar el commit, valida TODO lo siguiente. Si algo falla, regenera el mensaje; nunca te salgas de la convención:

* El tipo corresponde a la naturaleza del cambio y el Gitmoji corresponde al tipo.
* El staging representa una sola intención (no mezcla tipos).
* Formato `<gitmoji> tipo(scope): título`, con scope válido (dominio, no archivo).
* El título describe el estado final, no está en infinitivo, no expone detalles internos.
* El cuerpo explica el "qué" y el "por qué" en lenguaje natural, sin changelog ni enumeración de archivos.
* No contiene `Co-Authored-By`, créditos, firmas ni menciones de herramientas de IA.
* Si rompe compatibilidad, lleva `!` y el pie `BREAKING CHANGE:`.

Si detectas cualquier desviación, regenera el mensaje antes de continuar.
